# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

Mobile companion app (Expo, iOS/Android) for the French tabletop RPG **Prophecy 2e**. **Solo use is local-only** (SQLite on device, no account, no network); the **optional campaign mode** is the one exception — see the Campaign mode section below. UI is in **French**. See [README.md](README.md) for the feature tour, [DEV.md](DEV.md) for the contributor guide.

## Commands

```bash
bun install                       # setup (bun only — never npm)
bun run start                     # Metro
bun run android | ios | web       # build/launch (first native build is slow)
bun run test                      # vitest run (all)
bun run test:watch                # vitest watch
bunx vitest run src/lib/formula.test.ts          # single file
bunx vitest run -t "woundMalus"                  # single test by name
bunx tsc --noEmit                 # typecheck (the real gate — see lint note)
bunx drizzle-kit generate         # regenerate migrations after editing schema.ts
bun run build:catalogs            # data-src/*.csv → src/data/*-catalog.gen.ts (after ANY CSV edit)
bun run check:catalogs            # verify the .gen files match the CSV (no write)
```

Native modules (`expo-sqlite`, etc.) mean **Expo Go won't work** — a dev build is required. Adding a new native dep requires a dev-client rebuild (`bun run android`/`ios`).

`bun run lint` (`expo lint`) runs ESLint 9 flat config ([eslint.config.js](eslint.config.js), built on `eslint-config-expo/flat`); `tsc --noEmit` stays the type gate. **ajv trap:** `@eslint/eslintrc` needs ajv 6 but `expo-dev-launcher` pulls ajv 8 — the committed `bun.lock` pins ajv 6 at top with ajv 8 nested. Regenerating the lockfile can re-hoist ajv 8 and make ESLint crash at load (`Cannot set properties of undefined (setting 'defaultMeta')`); if that happens, ensure `node_modules/ajv` is 6.x and expo-dev-launcher has a nested 8.x.

## Architecture

**Stack:** Expo SDK 57 + expo-router (file-based routes under `src/app`, typed routes on), RN 0.86 / React 19.2, react-native-paper (Material 3), Drizzle ORM over expo-sqlite. React Compiler is on — avoid manual memo hacks that fight it. **expo-router does not sit on React Navigation** (that split landed in SDK 56): import `ThemeProvider` and the navigation themes from `expo-router/react-navigation`, and `BottomTabBarHeightContext` from `expo-router/js-tabs` — never from `@react-navigation/*`, which is no longer a dependency.

**The data split (central idea).** A character is stored across two 1:1 tables plus child tables ([src/db/schema.ts](src/db/schema.ts)):
- `characters` — the *sheet*: identity, stats, maximums, magic disciplines/sphere maxes. Changes rarely.
- `actual_state` — the *live in-play values*: current wounds, spent resources, magic reserve currents, money, initiative dice, conditions/notes. One row per character.
- `skills`, `armor`, `weapons`, `shields`, `items`, `spells`, `magic_reserves`, `effects` — N rows per character, FK cascade on delete. `magic_reserves` (issue #51) are reserve *objects*: each row is an independent pool (`max` + `current` both on the row, unlike the sheet/state split) and never touches the global réserve. `armor`/`shields` share most columns (prerequisites, creation, encombrement) but stay separate tables — see the `enchants` doc comment in schema.ts for why.

There is **no separate "status" screen**. Each character tab (`src/app/character/[id]/(tabs)/`) has a read mode and a live **edit toggle** (a FAB); edits write straight to `characters` or `actual_state` through `src/repositories/`, and screens refresh reactively via Drizzle's `useLiveQuery` (the DB is opened with `enableChangeListener`).

**French naming convention (follow it).** Generic columns are English; Prophecy game terms are French **stored without accents** (safe as DB keys) and **rendered with accents** in the UI. The mapping lives in [src/constants/prophecy.ts](src/constants/prophecy.ts): each domain entry's `key` matches a DB column, its `label` carries the accents. `NUMERIC_KEYS`, `asNumRecord`, `num`, `clamp` (in `lib/character-values`) derive stat columns centrally — reuse them instead of re-listing columns.

**SQLite is asynchronous — every `await` is real.** The driver is `drizzle-orm/sqlite-proxy` over expo-sqlite's **async** API ([src/db/client.ts](src/db/client.ts)), not `drizzle-orm/expo-sqlite`. Reason: expo-sqlite's *sync* API only exists on web behind a SharedArrayBuffer busy-spin bridge — it needs the page cross-origin isolated (COOP/COEP headers) and its first call times out while the wasm worker is still booting. The async API is plain postMessage, works with no special headers, so one code path covers native **and** web/desktop. Consequences:

- **Always `await`.** A dropped `await` no longer "just works" — the write genuinely hasn't happened yet.
- **Use `transaction()` from `db/client`, never `db.transaction` directly.** An async transaction is `BEGIN`/…/`COMMIT` as separate statements on one connection, so two overlapping callers would nest their `BEGIN`s and SQLite would reject the inner one. The helper serializes transactions app-wide; the sync driver got that for free.
- Transaction bodies are `async (tx) => …` and awaited properly. The old sync-only executors (`.run()`, `.all()`) are gone; `await tx.insert(...).values(...)` and `.returning().get()` are the idiom.
- The connection opens lazily in `connection()`, which also takes the pre-migration snapshot inside the same promise — so the backup always precedes the first query without any caller sequencing it. `useMigrations` is wrapped in [src/db/use-migrations.ts](src/db/use-migrations.ts) (Drizzle's expo hook is dialect-agnostic at runtime but typed for the sync driver; the cast lives there alone).
- Web needs `config.resolver.assetExts.push('wasm')` in [metro.config.js](metro.config.js), or expo-sqlite's `wa-sqlite.wasm` import fails to resolve at bundle time.

**Migrations & data safety.** Edit `schema.ts`, then `bunx drizzle-kit generate` (never hand-write SQL or touch `drizzle/meta/`; `generate` needs a real TTY for rename prompts). Migrations bundle via `drizzle/migrations.js` and apply in [`<DatabaseGate>`](src/components/database-gate.tsx) — mounted by `_layout` — with `useMigrations`. Before they run, the DB is snapshotted (`VACUUM INTO` → `prophecy.db.bak`, [src/db/backup.ts](src/db/backup.ts)); prod restores it on a failed migration instead of wiping. `created_at`/`updated_at` (and `effects.created_at`) use a drizzle `$defaultFn` and therefore have **no SQL default** — any raw insert into those tables must supply the timestamp.

**The database can be LOCKED rather than broken (web only).** expo-sqlite's web target keeps the DB in OPFS through wa-sqlite's `AccessHandlePoolVFS`, which holds *exclusive* sync access handles for the page's whole life — so the installed PWA and a browser tab on the same origin cannot both open it, and the loser gets a `NoModificationAllowedError` surfacing as `Failed query: CREATE TABLE … __drizzle_migrations`. **That is not a corrupt DB**: nothing was opened, so nothing was migrated, and running the restore/reset paths there would destroy good data over a stray tab. [lib/storage-lock.ts](src/lib/storage-lock.ts) `isStorageLockError` is the discriminator (text over the whole `cause` chain — a DOMException is not an `Error` subclass and does not exist in Node); `connection()` retries the open on a short bounded backoff, and `<DatabaseGate>` otherwise shows « Base de données verrouillée » with a **Réessayer** that simply remounts the gate — Drizzle's `useMigrations` migrates once per mount and has no retry of its own. There is no VFS knob in expo-sqlite to escape the lock; README documents the one-window-at-a-time rule for users.

**Never squash already-applied migrations.** Real testers run **mixed versions**, and the on-device migrator only tops up what each device is missing (SQLite has no `ADD COLUMN IF NOT EXISTS`, so one baseline can't both bootstrap a fresh install and top-up an old one). Keep the full `0000→N` chain; add new migrations on top. The forward-migration harness ([src/db/migrations.test.ts](src/db/migrations.test.ts)) guards this by seeding a DB at every prior version.

**Keep components small.** A screen is a composition of named pieces, not one 500-line function: when a block grows its own responsibility (a section, a card, a dialog), extract it — colocated for one-off pieces, `src/components/...` when reused. Same for shared logic: the campaign roster and the broadcaster both read projections through one hook ([use-character-projections.ts](src/hooks/use-character-projections.ts)) so a projection is assembled in exactly one place. Pure logic belongs in `lib/` where it can be tested — [skill-groups.ts](src/lib/skill-groups.ts) (the GM's COMP·MOD·TOT columns) and [skill-grouping.ts](src/lib/skill-grouping.ts) (the editor's filtering) came out of components for that reason.

**Tabbed screens are pagers.** A screen with in-page tabs (Compétences, Magie, Inventaire, la Compagnie) is built from [`<TabPager>`](src/components/ui/tab-pager.tsx): it owns the strip ([`<SubTabs>`](src/components/ui/sub-tabs.tsx), whose ink bar follows the scroll offset when a `progress` is passed) and lays the pages out in a paging `ScrollView` — deliberately NOT a native pager, so no dev-client rebuild and web keeps working. Consequences to respect: **the header is pinned and each page owns its vertical scroll** (wrap page content in [`<TabPage>`](src/components/ui/tab-page.tsx) for the standard padding + FAB clearance), pages mount lazily and stay mounted, and **no horizontal scrollable may live inside a page** — it would fight the pager. Pass `swipeEnabled={false}` where a swipe competes with the layout (the Compagnie does this above 840dp, since the split view's right pane owns its own gestures).

**Match the existing UI — never invent a new look for a widget that already exists.** Before adding a dialog, card, row, button or field, open the nearest existing one and copy its structure, styles and wording register. Concretely for dialogs: **never reach for Paper's `Dialog`/`Portal` directly — use [`<DsDialog>`](src/components/ui/ds-dialog.tsx)** (`visible` / `onDismiss` / `title` / `dismiss` / `actions`, children are the body). It owns the DS surface (18dp radius + 1px gold hairline, since Paper's corner balloons and it has no border), the tablet width cap, and — the part you cannot skip — a capped height with a scrolling body: Paper's `Modal` ignores the keyboard entirely and its `Dialog` has no max height, so a hand-rolled one puts its actions off-screen on a phone in landscape. Inside it: plain Paper `TextInput`s (no `mode="outlined"`, no `dense`) / `NumberField` for numbers, and the actions row is **two slots, not one list**: `dismiss` holds the way out (a plain **Annuler** / **Fermer**) pinned LEFT, `actions` holds what the dialog is for — the primary `mode="contained"` button with a `dsIcon(...)` — pinned RIGHT, where a second `mode="outlined"` action may sit beside it (the dice roller's « Tendances » next to « Lancer »). Never put the cancel back in `actions`: the split is what keeps a thumb from hitting « Annuler » on the way to the commit button. Live references: [campaigns/index.tsx](src/app/campaigns/index.tsx), [campaigns/[id]/index.tsx](src/app/campaigns/[id]/index.tsx), [dice-roller-dialog.tsx](src/components/dice-roller-dialog.tsx), [magic.tsx](src/app/character/[id]/(tabs)/magic.tsx). Confirmations and one-shot messages are **not** hand-rolled dialogs either: call `Alert.alert(title, message, buttons)` from [`@/lib/alert`](src/lib/alert.ts) — react-native's own signature, but ours renders the DsDialog above, on every platform. It replaced `react-native`'s `Alert`, which is `class Alert { static alert() {} }` on react-native-web: a literal no-op that made 26 confirms and error popups silently do nothing on the web build. Importing `Alert` from `react-native` is now an ESLint error. A destructive button takes `style: 'destructive'` (rendered in `colors.error`, since the OS red is gone with the OS alert) and the way out takes `style: 'cancel'` — [splitAlertButtons](src/lib/alert.ts) routes those into the same two slots, cancel LEFT. The queue and the split are pure and unit-tested; the rendering half is [`<AlertHost>`](src/components/ui/alert-host.tsx), mounted once under `<PaperProvider>`.

**Large screens.** Every responsive decision lives in [src/hooks/use-layout.ts](src/hooks/use-layout.ts) — branch on what it *returns* (`columns`, `nav`, `denseVertical`), never on a raw width, so a breakpoint move stays a one-file change. Stops follow the MD3 window classes (600 / 840) plus a `height < 500` guard, because a phone in landscape is "medium" by width with no vertical room. Every scroll container caps its content: `contentWidth` (720, reading width) by default, `useSplitWidth()` on screens that lay sections out with [`<Columns>`](src/components/ui/columns.tsx) — the two-column dealer used by the character tabs. Long lists that are really *tables* (skills) stay one column on purpose: splitting them breaks row grouping.

**Theming.** All colors flow through `useProphecyTheme()` — never hardcode. [src/theme/prophecyTheme.tsx](src/theme/prophecyTheme.tsx) maps ~11 design-system tokens (parchment & gold; Cinzel display + Noto Sans body, loaded in `_layout.tsx`) onto MD3 roles; the remaining ~20 roles are derived by tinting and tagged `DS` vs `derived` inline. Intentionally **not** re-themed: the Prophecy tendance trio (Dragon/Fatalité/Homme) in `constants/prophecy.ts` and the per-character dragon-accent palettes in [src/theme/dragonsTheme.tsx](src/theme/dragonsTheme.tsx).

**Catalogues are GENERATED from spreadsheets — never hand-edit the arrays.** The rulebook weapon/spell pickers read `src/data/*-catalog.gen.ts`, code-generated by [scripts/build-catalogs.ts](scripts/build-catalogs.ts) from `data-src/*.csv` (Excel, séparateur `;`, BOM/CRLF/multi-line quoted cells handled by the pure parser [src/lib/csv.ts](src/lib/csv.ts)). Edit the CSV → `bun run build:catalogs`. The `.gen.ts` files are **committed** so the app builds without the script; [src/data/catalog.test.ts](src/data/catalog.test.ts) re-runs the generator inside `bun run test` and fails when they drift from the CSV. Validation is strict and refuses to write anything on error: exact header match (a misspelled optional column would silently drop data), unique kebab-case ids, formulas through `lib/formula`, enums matched loosely (case/accents, key **or** label) against `constants/prophecy`. Adding a column means touching the CSV header, the `*_COLUMNS` list and the row builder together. CSV headers stay **French** (`nom`, `effet`, `duree`, `cibles`) — the spreadsheet is the authors' surface; English lives on the other side of the generator, in the DB columns and preset keys. `src/data/*-catalog.ts` holds only the `*Preset` types + a re-export; the weapon taxonomy sits in [src/data/weapon-constants.ts](src/data/weapon-constants.ts) so the generator never imports a file it generates.

**Pure engines (unit-tested, no DB).** [src/lib/formula.ts](src/lib/formula.ts) computes every formula in the app — a weapon's `FOR x2 +3 +1D10`, a spell's durée — through **one pipeline**: `parseFormula` → `computeFormula(formula, vars)` → `formulaResult(raw, vars)`. `vars` is a single `FormulaVars` bag (`carac`, `caracModifier`, `nr`, `sphere`); a caller fills whichever resolvers it holds and the engine never asks what kind of thing it is computing. **Any resolver may decline** (return null) and its term stays symbolic instead of silently counting as zero — that one rule is what lets the same function print « Sphère tours » with no character, « 5 + 3 × NR » before the roll, and a plain number once everything is known. `computeFormula` returns `{ total, symbolic }`, symbolic terms in source order; `formulaTermLabel` prints one.

Two variables are **opt-in at parse time** (`{ nr: true, sphere: true }`, or via `spellFormulaResult`) because a weapon has neither and letting them through would turn a typo into a valid formula. `NR` accepts every spelling the rulebook uses (`1 + NR`, `30 par NR`, `3+2/NR`, `NR x2`), all normalizing to `flat + coef × NR`. `SPHERE` scales off the caster's sphere: bare `SPHERE` means **the spell's own sphere** — what all 28 catalogue occurrences turned out to be — while `SPHERE_VENTS` names one explicitly, matched loosely (accents, case, prefix, singular/plural) so `SPHERE_VENT` works. Caracs need no opt-in and cover the one durée written against a stat (`VOL`, *Esprit du Gouffre*). [src/lib/modifiers.ts](src/lib/modifiers.ts) stacks roll modifiers: temporary `effects` add up, the **wound malus is the single worst active level (max, not sum)**, and modifiers fold into a caractéristique *before* a formula's multiplier. [src/lib/character-transfer.ts](src/lib/character-transfer.ts) is the zod-validated export/import envelope (carries an optional portable character `uuid` — see below). [src/lib/weapon-skill.ts](src/lib/weapon-skill.ts) resolves a weapon's compétence — see below.

**The test itself is [src/lib/roll.ts](src/lib/roll.ts)** — the whole rule set in one file, so a disagreement at the table is settled by reading it. `total = the dice's share + Σ context parts (+5 on a confirmed critique)`, réussite at `total ≥ difficulté` (15 by default), and **one NR per full step of 5 above it** — 20 is 1 NR, 25 is 2. A 10 and a 1 each call for exactly ONE reroll, never a cascade, and **the reroll never adds to the die**: it only confirms.

**Casting is its own kind of roll** (`RollContext.kind = 'cast'`, set by `spellRollContext`). Magic names its extremes **Miracle** / **Contrecoup**, gets **no +5** (a Miracle is a name, not five points — so a cast and an identical skill roll total differently), and — **only on the tendance trio** — makes the dice you did NOT keep matter: a discarded 10 or 1 rerolls and a confirmation is a **Contrecoup**, the 10 included, because the backlash is for ignoring the fluctuation rather than for rolling badly. The one case skipping the reroll: the **fluctuation die showing 1 while discarded** backlashes outright. The fluctuation is the **Dragon**, except for a **Sphère de l'Ombre** spell where the **Fatalité** takes its place. This mechanism belongs to the TENDANCES, not to having several dice — a spell rolled on plain dice (one or five, kept or summed) never invokes that power, so its discarded dice stay inert like any other roll's. `readDice` returns one `DieReading` per die and is the only place any of this lives; `confirms` is an array indexed like `dice`, since a cast on the trio can owe three rerolls at once.

The unit is a **`RollThrow`**, not a die, because effects grant extra dice two different ways: `keep` (the extras are alternatives, the player picks — the tendance trio is exactly this with three coloured dice) and `sum` (they add up). Whatever the count, **exactly one die can crit or fumble** — the one kept, or the **FIRST thrown** when summing; the rest are neutral however they land, and the UI draws them paler (`isNeutralDie`). Without that rule a fistful of dice makes a critique a formality. `naturalDie` is what the rules read and is never the sum: 7 + 3 totals ten but is not a *face* of ten, so there is nothing to confirm. Throw ORDER is therefore meaningful — nothing may sort `dice`. `resolveRoll` returns **null** while a `keep` throw has no pick yet, so no screen has to work out whether a roll is finished. A confirmed 10 is +5, i.e. one more NR; a confirmed 1 is a *flag*, not a penalty — the total stands and what it costs is the GM's business. Two fields carry the character's side and they are **not the same number**: `parts` (a LIST — a skill total, or MEN + VOL, or either plus a tendance die) feeds the total, while `confirm` is the character's own score in *what is being tested* — the **compétence's points** (never its TOT, which a D10 could never undercut), the **caractéristique**, or the **discipline** when casting (never the sphère, never the casting total). It cannot be derived from `parts` — a skill's TOT is in the sum while its points are not — so every context is built in one place, [lib/roll-context.ts](src/lib/roll-context.ts), and the engine never guesses. That file also owns the one arithmetic trap in the area: a **clé parfaite is +5 on the roll AND −5 on the difficulté shown by `SpellDetail`** — the same bonus from either side — so a cast counts it in the total and carries the spell's RAW difficulté.

**A weapon's attack total = its compétence's total.** `weapons.skillName` (nullable) is a **`skills.name`**, name-keyed like `skills.parentName` and the `skill:<name>` effect targets. Catalogue weapons arrive with it filled: `CATEGORY_SKILL` in [weapon-constants.ts](src/data/weapon-constants.ts) maps each picker category to a `DEFAULT_SKILLS` name and the generator bakes that into the preset, so **the category itself is never stored on a row** and the CSV needs no column. The two vocabularies are close but not equal — « Armes de corps à corps » → `Corps à corps`, « Armes à projectile » → `Armes à projectiles` (**manuel**, not physique) — which is why the attribut always comes from the *skill*, never hardcoded. [weapon-skill.ts](src/lib/weapon-skill.ts) resolves saved row → catalogue → `unknown`; a compétence with no points still yields a total (attribut alone, tagged « non acquise »), because looting a bow before learning to shoot is a real state. The bonus is `skillModifier`, the same one the Compétences tab and the GM's COMP·MOD·TOT columns use, so the two readings can't drift. Callers compute the reading and pass it to [`<WeaponCard>`](src/components/weapon-card.tsx) (like `SpellCard`'s `total`); a hand-made weapon picks its skill in [`<WeaponSkillField>`](src/components/weapon-skill-field.tsx) — base skills grouped by attribut, spécialisations as a second step.

**A spell's `effect` is the rulebook paragraph; everything else is a convenience layer.** `spells.effect` stays verbatim and untouched — it is the source of truth, and nothing rewrites it. Around it sit fields *extracted from that same paragraph*: `inGameEffect` (the mechanical half — numbers, durations, restrictions), `sensoryEffect` (what the character and witnesses perceive), `duration` + `durationUnit`, `targets`, and `tags`. **All optional, and that is the point**: the catalogue is filled one rulebook at a time, and a spell carrying none of them renders exactly the single « Effet » row it always did ([`<SpellDetail>`](src/components/spell-detail.tsx) falls back). Done so far: the 136 `livre-de-regles-2e-edition` spells (136 `inGameEffect`, 69 `sensoryEffect`, 115 `duration`, 136 `tags`); the other ~193 supplement spells are untouched.

Two rules when extending it. **Never invent rulebook text** — `sensoryEffect` is filled only where `effect` already describes something sensory, which is why it is empty on 45% of the spells. And **`duration` is authored, never regex-scraped**: 140 spells mention NR loose in prose (« un malus de 3+2/NR », « une personne par NR ») where the meaning lives in the sentence, so a scraper reaches ~59% coverage while silently getting the rest wrong. Hand-authoring reached 69% over the whole catalogue. The remaining third is deliberate: a durée the grammar cannot hold — « la Sphère des océans divisée par deux, arrondie au supérieur », « jusqu'au prochain lever du soleil » — is left EMPTY with the rule stated in `inGameEffect`, never approximated into a formula that would compute a wrong number.

**A picked spell remembers where it came from.** `spells.preset_id` (the CSV slug) + `spells.preset_revision` (a content fingerprint of the preset's `data`, [lib/preset-revision.ts](src/lib/preset-revision.ts), computed by the generator and baked into the `.gen.ts`) are stamped at pick time in [spell/catalog.tsx](src/app/character/%5Bid%5D/spell/catalog.tsx) and ride through export/import. Both NULL ⇒ **the player wrote it**, and no catalogue correction may ever touch it — provenance is recorded, never inferred from a name. Nothing consumes the revision yet; the propagation flow is in [ROADMAP.md](ROADMAP.md). A hash rather than an authored version column because the one time an author forgets to bump a number, the fix reaches nobody and nothing can detect it.

**An enchanted object remembers a spell the character may not know, and the roll that made it.** Somebody else usually did the enchanting — a character walks into a mage's shop and pays for it — so [enchant/catalog.tsx](src/app/character/%5Bid%5D/enchant/catalog.tsx) offers the **whole** catalogue, not the spellbook, and what it adds is a `spells` row with **`known: false`**: recorded because the enchant has to say what was cast into the object, kept out of the spellbook because the character cannot cast it. A flag on `spells` and not a copy onto the enchant, so a sortilège stays ONE shape everywhere and `SpellDetail` renders an enchant's source with no special case — the cost being that every reader of "the character's spells" must filter, which is what `knownSpellsQuery` is for (the Sorts tab, the GM's NPC gear; the enchant editor wants the unfiltered one). The catalogue badges the two states apart — « Déjà ajouté » vs « **Enchanté** » — because telling a player they already have a spell they cannot cast would talk them out of learning it. An unknown row is reachable from nowhere else, so [repositories/enchants.ts](src/repositories/enchants.ts) `setEnchantSource` prunes it once nothing points at it, checking references *before* deleting: `sourceSpellId` is `on delete set null`, so deleting a still-referenced spell would silently blank the OTHER enchants' links instead of failing.

`enchants.castScore` + `enchants.difficulty` are **the enchanter's roll, stored** — there is no score on this sheet to derive them from, and the app never rolls them (a number field, no dice). Both nullable: an enchant with no recorded numbers is a normal state, and a score *below* the difficulté is stored as readily as a good one — a botched enchantment is a fact. Everything else is derived by [lib/enchant-score.ts](src/lib/enchant-score.ts) and never stored (two numbers can't drift, five can): réussite, the NR — the one rule from `lib/roll`, imported rather than restated — and through the NR the durée and the cibles, which resolve to **real numbers** here where a spell card can only print them symbolically, because an enchant's NR was rolled once and is fixed forever. The sphère stays unresolved on purpose: it is the enchanter's, and this sheet does not know it.

**Export carries links as POSITIONS.** Child rows are exported as plain id-less arrays and re-inserted with fresh ids, so an enchant's target (`targetIndex` into weapons/armor/shields/items per `targetType`) and its source (`sourceSpellIndex`) travel as **indices into the sibling arrays of the same bundle** — which is why both halves of [repositories/transfer.ts](src/repositories/transfer.ts) select `orderBy(asc(id))` and the importer writes enchants LAST. An index over a uuid on every gear row: the bundle is self-contained so a position resolves exactly, while uuids would mean four columns, a backfill, and a minting rule everywhere gear is created or duplicated (`spawnNpc` included) — and a `targetUuid` can still join the shape later as an optional field without invalidating one existing file. An index that resolves to nothing drops the enchant rather than binding it to the wrong sword. `items` joined the bundle at the same time: they had simply never been exported.

`SPELL_TAGS` in [constants/prophecy.ts](src/constants/prophecy.ts) is **our** taxonomy, not the rulebook's — three axes (rôle / cible / contexte) whose job is to narrow 300+ spells to 20, not to encode rules. Being ours, its keys are **English** with a French `label`; the CSV is authored with the French labels and the generator normalizes them, the same path sphères and disciplines already take. When in doubt a spell gets fewer tags, never a new one.

**One time scale, `TIME_UNITS`.** Effect durations, spell cast times and spell durées all speak the same list (action → an, plus `cycle`, the Prophecy calendar unit a dozen enchantments use). It was briefly two lists and that was a mistake: a spell whose durée is « (1 + NR) semaines » has to become an `effects` row without a conversion step. Units never convert into one another — `tickUnit` decrements only the rows sharing the chosen unit — which is also why `cycle` can sit there at all (the rulebook gives it no equivalence in days, and nothing needs one). `PERMANENT_UNIT` stays outside the list so it never reaches a "temps écoulé" control.

**Portable character `uuid`.** `characters.uuid` (nullable at the DB level; backfilled on launch by `repositories/characters.backfillCharacterUuids`, minted for new rows via `$defaultFn` using [src/lib/uuid.ts](src/lib/uuid.ts) — a dependency-free RFC-4122 v4 so `schema.ts` stays Node-loadable by drizzle-kit/vitest). It's the stable id that survives export/import and device changes; the export preserves it on **restore** and mints a fresh one on **copy/clone** (`planImport` in `character-transfer.ts`). **The export intent decides which** (issue #43): a *sauvegarde* keeps the uuid, a *partage* strips it (`forSharing`) so the recipient gets a new lineage — two devices sharing one `charId` would fight over a single campaign roster row, and either one's `unshare` would purge the other. Chosen at write time in [`<ExportIntentDialog>`](src/components/export-intent-dialog.tsx), never guessed at import: `importCharacters(data, 'restore')` lets each bundle decide through `bundleMode` (uuid present ⇒ restore in place, absent ⇒ insert as a copy, reserves recharged).

## Diagnostic log — retrievable, never transmitted

A public-beta bug report needs evidence, and the app has no server to send it to.
[src/lib/log/](src/lib/log) is a local ring buffer (**1500 entries / 512 KB**,
whichever binds first) flushed to **two files**, `current` + `previous`;
`current` is **rewritten wholesale** on every flush (never appended), rotated at
launch, and anything past the 7-day window is purged. The **share sheet is the
only exit** — no server, no analytics, no automatic crash upload — and
[privacy.tsx](src/app/privacy.tsx) says so in plain French.

- **The redactor is the privacy boundary, and it is deny-first.**
  [redact.ts](src/lib/log/redact.ts) writes a payload key only if it is on
  `ALLOWED_PAYLOAD_KEYS` **and** absent from `USER_TEXT_KEYS` / `SECRET_KEYS` —
  the deny check runs first, so allow-listing `nom` by accident still drops it.
  [redact.test.ts](src/lib/log/redact.test.ts) asserts that inversion; don't
  defeat it. Records are named by opaque local id (`characterId`, `uuid`), a
  patch by its **column names** (`fields`), never by a value. Everything dropped
  is counted as `_dropped: n`. Strings truncate at 400, stacks at 2000. Keep this
  module free of framework imports — like the other pure engines, it must load in
  plain-Node vitest.
- **Layering.** `types` → `redact` / `ring-buffer` / `serialize` / `session` (all
  pure, all tested) → `logger.ts` (the engine: injected sink + clock, level
  filter, 2 s debounce, immediate flush on `error`) → `index.ts` (the singleton:
  platform sink, level persisted in AsyncStorage, launch rotation). Native-module
  glue lives apart in [share.ts](src/lib/log/share.ts) so `index.ts` stays
  importable anywhere.
- **The sink is platform-split behind one interface** (`LogSink`): Metro picks
  `sink.native.ts` (two files under the private document dir) or `sink.web.ts`
  (localStorage); `sink.ts` is the in-memory default Node gets. The sink is dumb
  read/write/remove — rotation and retention are pure decisions taken above it
  from the entries' own timestamps.
- **The logger starts with NO sink** and gets one at the end of `initDiagnostics`.
  That is not cosmetic: a flush firing first would overwrite `current` while it is
  still the previous launch's file waiting to be rotated.
- **Session id is random per launch, never persisted, not device-derived**, so two
  shared reports can't be correlated.
- **Capture:** `installCapture()` (global handler, unhandled rejections,
  background flush) runs at _layout **import time**, above the tree;
  [`<LogErrorBoundary>`](src/components/log-error-boundary.tsx) catches render
  throws; `useRouteBreadcrumbs` logs `route.change`; repositories call
  [`logWrite`](src/repositories/log.ts) — `update` at `debug` (a stat stepper
  fires on every tap), `insert`/`delete` at `info`. Default level is `info` in
  prod, `debug` in dev.

## Campaign mode — a LOCAL table, optionally networked

A GM's **table** is local-first and works with no network at all: NPCs, their sheets, wounds and initiative live in this device's DB. Attaching a relay **server** ([separate repo](https://github.com/aehru/ProphecyCompanionServer): FastAPI + WebSocket + SQLite; deploy behind Caddy for TLS) is the *bonus* — it adds the players' characters, which they broadcast as a **minimized, read-only projection**. The full wire contract is [docs/campaign-protocol.md](docs/campaign-protocol.md). Solo use is untouched — only an opted-in character's projection ever leaves the device.

**Code is English, UI is French**: `npc` in columns/identifiers, « PNJ » on screen.

- **The roster is a merge, local first.** [src/lib/roster-merge.ts](src/lib/roster-merge.ts) `mergeRoster(local, remote)` (pure + tested — the local entry WINS on a charId collision, so a server echo can't roll back a wound you just marked). Local half: [src/hooks/use-local-roster.ts](src/hooks/use-local-roster.ts) projects the table's own character rows through the same `toSharedCharacter` used on the wire. Remote half: [src/hooks/use-gm-roster.ts](src/hooks/use-gm-roster.ts), which simply never connects when no relay is attached. Both are assembled once for the whole campaign subtree by [`<TableRosterProvider>`](src/components/campaign/table-roster-provider.tsx) (`connected` tells the UI whether a server exists at all).

- **The projection is the privacy boundary.** [src/lib/character-share.ts](src/lib/character-share.ts) `toSharedCharacter` emits ONLY: `nom`, caractéristiques, attributs, tendances, wounds, resources (maîtrise/chance), initiative, conditions, `skills` (**trained only**, value>0, with attribut + spec link), `effects` (**active only**, non-expired bonus/malus). **Excluded on purpose:** concept, biographie, notes, money, magic, untrained skills, expired effects. A **data-minimization test** fails if the wire widens beyond this allowed set — don't defeat it. `SHARED_SCHEMA_VERSION` is `2` (skills+effects added; evolve additively).
- **Wire layer is pure + tested.** [src/lib/campaign-protocol.ts](src/lib/campaign-protocol.ts) (message builders, tolerant zod parser, URL/scheme + join-link helpers) and [src/lib/campaign-client.ts](src/lib/campaign-client.ts) (reconnecting `CampaignSocket`, injectable WS). Mirror any wire change into the server's pydantic `app/schemas.py` — the two languages are hand-synced.
- **Live broadcast is app-level, not screen-scoped.** [src/hooks/use-campaign-live.tsx](src/hooks/use-campaign-live.tsx) provider (mounted in `_layout.tsx` above the Stack) keeps ONE campaign broadcasting on any screen while foregrounded; global floating indicator ([src/components/campaign-live-indicator.tsx](src/components/campaign-live-indicator.tsx)). Broadcasts ALL characters shared into the campaign on ONE socket (protocol v2 — hello has no charId, share/unshare frames carry it; a GM publishes NPCs the same way via `gmHello`, but ONLY with `campaigns.share_npcs` on — off by default, since the roster reads them locally; the co-GM case is the reason the path exists). Pushes when a character's **projection** changed ([src/lib/campaign-live.ts](src/lib/campaign-live.ts) `projectionSignature` — in-play values AND sheet edits, so finishing a character edit syncs to the GM), per-char signature on a shared 5s debounce; unsharing while live sends `unshare` on the live socket (paused → `unshareFromServer` purge). Stop = pause (last state stays on server); auto-resumes across restart (AsyncStorage). GM identity = portable `gmToken` (server stores only its hash), NOT a device id.
- **Tables** ([schema.ts](src/db/schema.ts)): `campaigns` (`code`/`server_url`/`gm_token` all **nullable** — a GM row exists before any server; `share_npcs` opt-in), `campaign_shares` = **membership** (GM side it IS the roster; player side it is what gets broadcast), `gm_notes` (GM device only, keyed by `charUuid`). `characters.kind` is `'pc' | 'npc'` — a label only (NPCs are full character rows, listed with the PCs behind a badge). Repo: [src/repositories/campaigns.ts](src/repositories/campaigns.ts): `createLocalTable` (no network), `attachServer` (mints the code later), `setMember`, `createNpc`, `setShareNpcs`.
- **GDPR/consent:** persistent disclaimer on the campaign list (covers the GM), a contextual line in the join dialog (QR/deep-link joins land there directly), and [PRIVACY.md](PRIVACY.md) distinguishes solo (local) from campaign (opt-in projection under the host's responsibility). Leave/stop purges the server row.
- **GM tooling on the Compagnie screen** ([compagnie.tsx](src/app/campaigns/[id]/compagnie.tsx)): roster cards show the *projection*, so editing an NPC reaches back to the local row through `characterByUuidQuery` (`charId` IS `characters.uuid`) — [`<NpcInPlayEditor>`](src/components/campaign/npc-in-play-editor.tsx) edits `actual_state` only, reusing the Fiche's own sections via their `editing` prop. A player's character stays read-only AND projection-limited (one-way protocol); a GM's own NPC also gets [`<NpcGearSections>`](src/components/campaign/npc-gear-sections.tsx) — armes/armures/boucliers/sorts read from the local rows, with damage formulas resolved through the same wound+effects modifier the Fiche uses. `spawnNpc` duplicates an NPC for the "three gardes, three wound tracks" case, numbering names with [npc-name.ts](src/lib/npc-name.ts). The Initiative tab ranks *one row per die* ([initiative-order.ts](src/lib/initiative-order.ts) — pure + tested; wounded value, unusable dice last). Above 840dp the screen splits: roster left, [`<GmSheetBody embedded>`](src/components/gm-character-sheet.tsx) right; below, that same body renders inside the bottom-sheet Modal.
- **Known wart** (documented in [ROADMAP.md](ROADMAP.md)): with `share_npcs` ON a GM device holds two sockets (roster socket + app-level live socket) — duplicate frames, harmless; merge later. Off (the default) there is only one.

## Testing

Vitest runs in a **Node** environment ([vitest.config.ts](vitest.config.ts) mirrors the `@/` → `src` alias). Three kinds work today: pure logic (`lib/*`); the **forward-migration harness** ([src/db/migrations.test.ts](src/db/migrations.test.ts)) — it replays `drizzle/*.sql` against `better-sqlite3`, seeding a DB at each prior schema version to catch NOT-NULL-without-default, tightened CHECKs, and journal drift; and the **catalogue freshness check** ([src/data/catalog.test.ts](src/data/catalog.test.ts)), which re-runs the CSV generator and diffs it against the committed `.gen.ts`. Two suites are privacy guards rather than correctness ones and must not be relaxed to make a change pass: `character-share.test.ts` (the campaign wire) and [redact.test.ts](src/lib/log/redact.test.ts) (the diagnostic log's allow-list). **Run tests after every `drizzle-kit generate`.** Repository logic still isn't covered — it imports the `db` singleton — but the sqlite-proxy switch put the seam in place: the driver is one async `(sql, params, method)` callback, so pointing it at `better-sqlite3` in Node is now the whole of the dependency injection.
